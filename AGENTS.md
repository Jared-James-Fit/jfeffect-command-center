- Logging Level points are awarded only by DB triggers into `athlete_xp_events` with unique per-record/day/week `source_key`s — why: idempotent, no client-side farming, history backfillable.
- Achievement "seen" state lives in `athlete_achievement_views` (server-side), never localStorage — why: reveals must not replay across devices.
- Member-made chats (`chat_groups.kind` = `'direct'` 1:1s and `'crew'` groups) are private to their members: staff RLS, group lists and "View as client" must never include them, and request/invite state (accept, join, decline, block, remove, report) changes only through `chat_direct_respond` / `community_message_author` / `crew_*` — why: declines and removals must stay silent (nobody can tell a decline from unread) and reports are the coach's only window in.
- PT session sync and reminder bookkeeping (`gcal_dirty`, `time_set_at`, `reminder_24h_sent_at` reset on move, auto-closing `pt_session_change_requests`) is done by DB triggers on `pt_sessions`, never by callers — why: sessions are edited from several screens, and every path must move Google and the evening-before text with it.
- Google events from several calendars are merged per occurrence (`mergeGoogleCalendarLists`: iCalUID + original start), never by iCalUID alone, and listing follows `nextPageToken` — why: every repeat of a recurring event shares one iCalUID, so UID-only dedupe shows a weekly event once and the double-booking check misses the rest.
- Online booking (`/book/<slug>`, booking.server.ts): a public, signed-out booking is always an `appointments` row and never touches session credits, even when the email matches a client; credit-using `pt_sessions` are only created for a trusted identity (signed-in client, or a staff-minted personal link `?i=` verified by `booking-invite.server.ts`). Every online booking holds its time in `booking_slot_claims` (overlap-excluded) around the final re-check, and Google must be readable on every calendar (`requireAll`) or no times are offered — why: anyone can type a client's email, two people can tap the same slot, and a time we couldn't check could double-book.
- Booking types live in `booking_cards` (+ `booking_card_hours` for online hours); `booking_links` / `booking_link_availability` are retired history — why: one list for in-app booking and shareable links.
- A staff login linked to the person's own client account (`community_profiles.same_person_as`, written only by the admin-only `linkTeamMemberClient`) gets read-only "Linked login reads own …" RLS on the client-calendar tables via `public.linked_client_id()`; any new table the client calendar reads needs the same policy — why: client-read rules check `clients.user_id = auth.uid()`, so without it the staff home's "My calendar" is empty for the person themselves (it only looked right in the owner's preview).
- Client "Connect Google Calendar" (`client-gcal.server.ts`) uses the client's own Google sign-in with only `calendar.app.created`, writes only to the "JF Effect" calendar it created, keys events by `googleEventId(feed uid)` and only deletes events it tagged (`extendedProperties.private.jf`); its content comes from `buildClientFeedEvents`, the same as the feed — why: one source for what's in a client's calendar, no access to anything else in their Google account, and re-syncs never duplicate or touch their own events. The Google button is offered only while `clientGoogleReady()` passes (keys checked with Google, cached in `app_settings.client_google_calendar_check`; a broken setup raises one `google_calendar_setup` support alert) — why: a wrong or leftover client id sends clients to Google's "OAuth client was not found" page.
